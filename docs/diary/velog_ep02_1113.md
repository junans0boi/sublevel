# "방 하나에서 하는 느낌" — 게임 제작기 #2 상담 채팅을 해고하고, 섬과 엘리베이터와 오토바이

> 지난 화: 23시 49분, 테스트 100개가 통과한 빌드에 나는 "너무 어색함"이라고 적었다. 그 피드백으로 다음 지시문을 쓰던 상담 채팅은 코드도 빌드도 볼 수 없었다.

11분 뒤, 자정. 나는 그 상담 채팅을 해고했다. 이날은 그렇게 시작해서 밤 11시 26분에 끝났다. 커밋 78개, 그중 22개가 브랜치 합치기(merge)였다.

## 00:00, 상담 채팅의 해고

그때까지는 따로 띄운 상담 채팅이 방향을 잡고 다음 지시문을 써 줬다. 그런데 그 녀석은 게임을 볼 수 없었다. 내가 보내는 사진과 로그로만 판단했다. "어색하다"는 말을 들어도 무엇이 어색한지 직접 확인할 방법이 없었다.

그래서 그 역할을 **프로젝트 세션이 직접** 맡게 했다(ADR-047). 기술 리드, 구현자, 검수자를 한 몸에. 사람 눈과 손으로만 알 수 있는 건 "직접 확인 목록"으로 나에게 넘긴다.

*00:00, 상담 채팅의 해고. ADR-047 기록으로 다시 그린 그림.*

새 검수자의 첫 성과가 꽤 좋았다. 빌드를 돌려 화면 53장을 저장해 직접 열어 보더니, 옆으로 걸을 때 **캐릭터 몸 전체가 옆을 보고 달린다**는 걸 찾아냈다. 에셋의 옆 달리기 동작이 게걸음이 아니라 몸을 90° 돌려 뛰는 동작이었다. 이동 중 조준하면 총도 25° 틀어져 있었다. 다리만 돌리고 상체는 정면을 보게 바꿨다(ADR-049). 내가 "어색함"이라고만 적은 것의 정체를, 처음으로 AI가 자기 눈으로 찾았다.

## 01:45, "방 하나에서 하는 느낌"

같은 새벽, 내가 한 말이 결정 기록에 들어갔다(ADR-050).

> 맵이 너무 작고, 지역과 지역을 바다·차도·산으로 이동하는 게 아니라 방 하나에서 하는 느낌

나는 **이동하고, 싸우고, 또 이동하고, 싸우는** 배틀로얄을 생각했다. 그런데 나온 건 서든어택처럼 한 공간에서 싸우는 것, 그 이상도 이하도 아니었다. 정확히 어느 화면을 보고 한 말인지는 기록에 없다. 회색 상자 방이었는지, 전날 밤의 160×120m 공장이었는지. 아마 둘 다였던 것 같다.

이 한 문장으로 0화의 기획이 뒤집혔다. 닫힌 시설 구역 7개가 **하나로 이어진 야외 맵**이 됐다. 지역은 산·도로·물로 나뉘고 걸어서 오간다. 엘리베이터는 지역마다 있는 투입구가 됐다. 비행기 낙하 대신 무작위 지역의 엘리베이터에서 내려, 가까운 집에 뛰어 들어가 파밍한다.

같은 커밋에 전날 불만도 한 번에 처리됐다. 진짜 HUD, Tab 인벤토리, Esc 메뉴, 모든 글자 한글. 연사가 끊기던 것도 고쳤다. 서버가 "조금 일찍 온" 사격 요청을 버려서, 0.11초마다 쏴야 할 총이 0.22초 공백을 내고 있었다(ADR-051).

## 아침: 묻지 말고, 여럿이서

맵을 다시 만들려면 일이 많았다. 그래서 지시를 하나 더 했다. **묻지 말고 판단대로, 서브 에이전트를 병렬로**(ADR-052).

AI가 스스로 정한 1차 설계는 **1024×1024m 섬**, 지역 4개(산악·공장·마을·습지). 지역 사이는 능선·절벽·강으로 막고, 고개와 다리로만 잇는다. 맵은 손으로 찍지 않는다. AI는 에디터에서 마우스로 땅을 칠할 수 없으니, 데이터 → 생성기 → 규칙 검사기 → 빌더 순서로 코드가 섬을 만든다. 같은 시드면 같은 섬이 나오니 검사도 된다.

같은 시각, 다른 에이전트들은 `PUBG_GAP.md`를 채우고 있었다. 이 문서의 출발점은 내 말이었다. **"배틀그라운드랑 비교해서 부족한 것 보완"**(ADR-053). 앉기, 낙하 피해, 헤드샷, 킬 로그, 수류탄, 헬멧·조끼. 이날부터 기능 목록의 기준은 "배그에 있는데 우리에게 없는 것"이 됐다. 몸풀기 게임이라는 말은 여전히 어디에도 없었다.

09시 50분, **봇의 머리**가 들어왔다. 배회, 줍기, 소리 확인, 교전, 후퇴, 회복. 여섯 가지 상태를 오간다. 첫날의 더미가 드디어 움직이기 시작했다.

10시 54분, 이 섬이 게임의 첫 장면이 됐다.

## 15:53, "차량(급함)"

오후에 디테일 묶음을 한꺼번에 던졌다(ADR-065). 엘리베이터는 지하에서 올라오게. 자동 달리기, Alt 자유 시점, 천천히 걷기, 핑, 파쿠르. 그리고 기록에 이렇게 적혀 있다. **"차량(급함)"**. 거기에 한마디 더 얹었다.

## 📚 이번 회차에 알아두면 좋은 용어

### 워크트리와 브랜치 병합 (git worktree & merge)
**한 줄 정의:** 워크트리는 한 저장소에서 작업 폴더를 여러 개 꺼내 쓰는 기능. 각 폴더가 자기 브랜치를 가져서 여러 명이 서로 파일을 덮어쓰지 않고 동시에 일할 수 있다. 끝나면 **병합(merge)**으로 하나로 합친다.

**우리 게임에서는:** 에이전트마다 워크트리를 하나씩 받아 기능을 만들고, 통합 브랜치(`integration/wave2`, `integration/wave4`)로 모았다. 실제 커밋 기록이다.

```
12:38 Merge branch 'worktree-agent-ae67ede199fccef3c' into integration/wave4
12:38 Merge branch 'worktree-agent-a4628fd61c83d60be' into integration/wave4
12:39 Merge branch 'worktree-agent-a70c78e9ab7d53f9e' into integration/wave4
```

**왜 중요한가:** 병렬로 일하면 빨라지지만, 합칠 때 처음 부딪친다. 17시 17분의 "first Unity compile"처럼 합친 뒤 검증하는 단계가 꼭 필요하다.

### 시드 난수 (Seeded RNG)
**한 줄 정의:** 시드는 난수 생성기의 출발 숫자. 같은 시드를 넣으면 매번 똑같은 "무작위" 결과가 나온다.

**우리 게임에서는:** 누가 어느 엘리베이터에서 시작할지를 시드로 정한다.

`Assets/_Project/Scripts/Core/Deployment.cs`
```csharp
// Which elevator each participant (players and bots alike) starts in (ADR-055 (1)(4)). Pure and deterministic:
// the same participants, elevators and seed always give the same answer.
```

**왜 중요한가:** 테스트하려면 재현이 돼야 하고, 게임이 재밌으려면 매 판 달라야 한다. 시드 12345가 고정돼 매 판 같은 최종 지역이 나온 건, 그 둘 사이의 스위치를 깜빡한 사례다.

### 상태 머신 (State Machine)
**한 줄 정의:** 캐릭터가 "지금 무슨 상태인지"를 몇 개로 정해 두고, 조건에 따라 상태를 옮겨 가게 하는 설계.

**우리 게임에서는:** 봇의 머리가 6가지 상태를 오간다. 이 판단 부분은 Unity와 상관없는 순수 C#이라 화면 없이 테스트할 수 있다.

`Assets/_Project/Scripts/Core/BotBrain.cs`
```csharp
public enum BotState { Roam = 0, Loot = 1, Investigate = 2, Engage = 3, Retreat = 4, Heal = 5 }
```

**왜 중요한가:** "똑똑한 봇과 싸우는 연습 게임"이 처음 의도였다. 봇이 지금 왜 그렇게 움직이는지 설명할 수 있어야 고칠 수도 있다.

### 소유권 (Ownership)
**한 줄 정의:** 네트워크 게임에서 어떤 물체를 **누가 직접 움직일 권리**를 가졌는지. 1화의 서버 권위와 짝이 되는 개념이다.

**우리 게임에서는:** 원칙은 서버 권위지만 차는 예외다(ADR-069). 운전자 PC가 차를 소유하고 직접 굴린다. 서버를 거치면 핸들을 꺾은 뒤 반응이 늦어지기 때문이다. 운전석이 비면 서버가 소유권을 되찾는다.

`Assets/_Project/Scripts/Net/Vehicle.cs`
```csharp
void ServerFollowDriver()
{
    var driver = FindCombatant(Seat0.Value);
    if (driver != null && driver.Owner.IsValid)
    {
        if (Owner != driver.Owner) GiveOwnership(driver.Owner);
    }
    else if (Owner.IsValid) RemoveOwnership();
}
```

**왜 중요한가:** 보안(서버 권위)과 조작감(즉시 반응)은 서로 당긴다. 어디서 예외를 둘지 정하는 게 네트워크 게임 설계의 핵심이다.
