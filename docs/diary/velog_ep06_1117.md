## 아침: 내가 직접 해 봤다

자고 일어나서 빌드를 받아 직접 해 봤다. 남긴 말은 세 줄이다.

펀치는 서버 판정이 멀쩡했다. 주먹은 약 1.2m까지 닿는데 봇은 1.5m에서 휘둘렀다. 허공에 주먹질을 한 거다(ADR-218). 파밍은 건물 411채에 아이템 자리가 900개, 건물당 두 개꼴이었다. 1,262개로 늘리고 건물마다 무기가 최소 하나는 나오게 했다(ADR-256).

제일 어이없던 건 세 번째였다. 캐릭터가 걸을수록 땅속으로 내려갔다. 범인은 어젯밤 테스트를 통과한 그 발 IK였다. 발을 땅에 붙이려고 골반을 내리는데, 그 값을 매 프레임 새로 정하지 않고 지난 값에 더해 갔다. 평지에서 최대 0.26m, 15도 경사에서는 평균 0.235m가 박혀 있었다(ADR-262).

10시 54분, master 인수인계 문서에 이런 줄이 남았다. 내가 "나에게 묻지 말고 알아서 해"라고 한 뒤로 병합·커밋·빌드는 master가 한다. 그날 나머지는 정말 그렇게 굴러갔다.

## 📚 이번 회차에 알아두면 좋은 용어

### IK와 누적 버그 (Inverse Kinematics & Integrator Bug)
IK(역운동학)는 "발을 여기에 놓고 싶다"는 목표를 주면 무릎과 골반 각도를 거꾸로 계산하는 기법이다. 누적 버그는 매 프레임 값을 새로 정하지 않고 지난 값에 더해 가서 오차가 쌓이는 실수다.

**우리 게임에서는** `Assets/_Project/Scripts/Gameplay/CombatantAnimation.Gait.cs`가 발을 땅에 붙이려고 골반을 내린다. 커밋 `b1ca398c`의 전/후 한 줄이다. 전에는 지난 프레임 값(`_plantDrop`)에서 빼 나갔고, 후에는 발밑 땅까지의 거리로만 정한다.

```csharp
// 전
float dropTarget = Mathf.Clamp(_plantDrop - Mathf.Min(want[0], want[1]), 0f, PlantMaxLower);
// 후
float dropTarget = Mathf.Clamp(Mathf.Min(needHigh, needLow + PlantMaxSplit), 0f, PlantMaxLower);
```

**왜 중요한가** 누적 버그는 잠깐 보면 멀쩡하고 오래 돌려야 드러난다. 그래서 '멈춰 서서 발 높이'만 재는 테스트로는 안 잡힌다.

### 공간 해시 (Spatial Hash)
맵을 바둑판 칸으로 나누고 물체를 칸별로 담아 두는 방법이다. "내 주변 25m 안에 뭐가 있지?"를 물을 때 전체를 다 보지 않고 근처 칸만 본다.

**우리 게임에서는** `Assets/_Project/Scripts/Core/World/PointGrid.cs`. 봇 79마리가 아이템 1,262개와 문을 매번 전부 훑던 것을 근처 칸만 보게 바꿨다(ADR-290).

```csharp
static long Key(int cx, int cz) => ((long)cx << 32) ^ (uint)cz;
int CellOf(float v) => (int)Math.Floor(v / _cell);
```

**왜 중요한가** 봇 수 × 물체 수만큼 검사하면 80명 판에서 서버가 못 버틴다. 칸으로 나누면 검사가 주변 몇 칸으로 줄어든다.

### 매칭 대기열 (Matchmaking Queue)
"게임 시작"을 누른 사람들을 서버가 줄 세워 두었다가, 정해진 조건이 되면 한 판으로 묶는 장치다.

**우리 게임에서는** `Assets/_Project/Scripts/Core/MatchQueue.cs`(ADR-247). 첫 사람이 들어오면 30초 창이 열린다. 창이 끝나거나, 사람이 꽉 차거나, 못 들어가는 파티가 생기면 바로 시작한다. 남는 자리는 봇이 채운다.

```csharp
public bool ShouldStart(TeamMode mode, double now, TeamRules teams)
{
    if (_tickets.Count == 0) return false;
    if (SecondsLeft(now) <= 0f) return true;
    var plan = Compose(mode, teams);
    return plan.Overflow.Count > 0 || plan.Humans >= _rules.MaxHumans; // full: no reason to wait
}
```

**왜 중요한가** 너무 오래 기다리게 하면 사람이 떠나고, 너무 빨리 시작하면 판이 봇뿐이다. 이 30초가 다음 날 "대기 섬"이라는 새 문제로 이어진다.

### 홈페이지 → 런처 → 전용 서버 구조
온라인 게임을 배포하는 흔한 모양이다. 홈페이지에서 런처를 받고, 런처가 로그인·업데이트·실행을 맡고, 게임은 회사가 운영하는 전용 서버에 접속한다.

**우리 게임에서는** 이슈 #379에서 정했다. 사이트와 백엔드는 별도 저장소(`sublevel-web`, `sublevel-backend`), 런처는 다음 날 생긴 `sublevel-launcher`. 게임 서버는 이 저장소의 `Assets/_Project/Editor/BuildScript.cs`가 Linux ARM64용으로 따로 빌드한다. 아키텍처를 직접 지정하는 첫 줄이 ADR-296의 교훈이다.

```csharp
public static void BuildServerLinuxArm64()
{
    EditorUserBuildSettings.SetPlatformSettings("Linux64", "Architecture", "ARM64");
    Debug.Log($"[BuildScript] Linux Architecture setting = {EditorUserBuildSettings.GetPlatformSettings("Linux64", "Architecture")}");
    Build(BuildTarget.StandaloneLinux64, "Build/server-linux-arm64/SublevelServer", ScriptingImplementation.IL2CPP, server: true);
}
```

**왜 중요한가** 조각이 하나 늘 때마다 "어디서 깨졌나"를 찾을 곳도 하나 는다. 연습 게임에는 필요 없던 구조다. 이 구조가 생긴 순간이 곧 의도가 바뀐 순간이었다.
