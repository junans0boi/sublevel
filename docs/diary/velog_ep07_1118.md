# 봇들이 3분 만에 30명씩 죽던 날 — 게임 제작기 #7 빈손 봇, 그리고 대기 섬 첫 삽

> 지난 화: 이슈 #379 한 줄로 연습 게임에 홈페이지가 생겼다. 봇은 파밍을 배웠지만, 빈손 봇은 적을 보면 물러나기만 했다. 그리고 사이트에서 게임으로 들어갈 문, 런처와 로그인은 아직 없었다.

## 새벽 1시 28분, 문이 생겼다

자정을 넘기자 어제 정한 구조가 실제로 붙기 시작했다. 1시 19분 사이트에 구글 로그인 버튼이 달렸고, 1시 28분 런처의 첫 커밋이 올라왔다. Tauri로 만든 작은 앱이다. 구글로 로그인하고, 게임을 내려받고, 실행한다. 1시 50분에는 사이트 첫 화면도 한 번 갈아엎었다.

![사이트 개편](img/ep07/site_redesign_1118.jpg)
*11/18 01:50 사이트 개편. 오른쪽 위에 로그인이 생겼다(저해상도 캡처).*

2시 30분에는 작은 사고도 있었다. 모델 파일이 없는 작업 폴더에서 Unity를 돌렸더니, 짝 잃은 `.meta` 파일 120개를 Unity가 지워 버렸다. 바로 복구했다.

오전에는 런처에 디자인이 입혀졌다. 왼쪽에 B1부터 B8까지 층 버튼이 있고, 첫 화면 이름이 "지하 1층 · 출발 대기"다. 런처마저 엘리베이터였다.

## 오전 11시 40분, 빈손 봇이 주먹을 쥐었다

엘리베이터에서 막 내린 봇은 총이 없다. 어제까지는 적을 보면 물러나기만 했다. 그래서 규칙을 줬다(ADR-310).

- 상대도 빈손이면 주먹으로 싸운다
- 상대가 총을 들었으면 시선이 끊기는 곳으로 도망간다. 주변 8방향 × 3거리 후보 중 적의 시야가 막히는 곳을 고른다
- 싸움이 끝나고 6초간 조용하면 근처 시체에서 총과 방어구를 줍는다

도주 성공률은 68%였다. 숫자만 보면 잘 된 것 같았다. 그런데 80명 판을 돌려 보니 다른 데서 터졌다.

![사망 구성 차트](img/ep07/chart_deaths.png)
*총을 줍기도 전에. 사망 66건 중 37건이 빈손끼리 주먹싸움이었다(ADR-310·315 측정값).*

무기를 얻은 봇은 79명 중 27명뿐이었다. 다들 총을 줍기도 전에 서로 때리다 죽었다. 그래서 빈손 봇은 12m 밖의 빈손 적은 무시하고 하던 파밍을 계속하게 했다(ADR-314). 오후에는 봇이 할 일을 고르는 순서표도 생겼다. 탈출, 교전, 파밍, 총성 조사, 집결, 이동 순서다(ADR-312).

솔직히 봇이 너무 열심히 싸워서 문제가 될 줄은 몰랐다. 배그도 초반에는 다들 파밍부터 한다. 그 흐름을 봇에게 가르치는 게 생각보다 어려웠다.

## "시작 2~3분 만에 30명이 줄어든다"

이날 내가 한 말 중 제일 큰 일을 만든 문장이다. 어느 판을 보고 한 말인지는 기록에 없다. 아마 서버에 올라간 판을 보다가 한 말이었던 것 같다.

재 보니 투입 후 3분 안에 25~59명이 죽고 있었다. 밤 9시 10분, **초반 평화**를 넣었다(ADR-315). 투입 후 5분 동안은 가까이 붙은 적이 아니면 먼저 상대하지 않는다.

첫 측정은 그대로였다. 평화 거리를 4m로 잡았는데 사망이 52~56명. 들여다보니 대부분 투입 후 4~10초 안에 빈손끼리 주먹싸움을 하다 죽었다. 엘리베이터 문이 열리자마자 싸운 거다. 그래서 둘 다 빈손이면 거리와 상관없이 서로 건드리지 않게 바꿨다.

## 0/20의 범인

새벽부터 밤까지 틈틈이 **동기화 측정**이 돌았다. 서버가 시간을 되감아 "쏜 순간 적이 어디 있었나"를 보는 되감기가 핑마다 제대로 맞는지 보는 측정이다.

이상한 숫자가 나왔다. 멈춰 있는 표적인데 0/20, 한 발도 안 맞는 회차가 있었다. 1시 48분에 찾은 원인은 게임이 아니라 **측정 도구**였다. 사격자를 제자리로 옮긴 뒤, 서버가 그걸 반영하기도 전에 쏘고 있었다.

밤 9시 38분에 하나 더 찾았다. 사격자가 3.5초 장전하는 동안 움직이는 표적이 걸어서 벽 뒤로 들어가 버렸다. 이것도 측정 도구 문제였다. 고친 뒤 결과는 이랬다.

![핑별 결과 표](img/ep07/table_ping.png)
*0/20의 범인은 측정 도구였다. 고친 뒤 핑 100ms까지 전부 합격.*

10시 8분에 결론이 났다. "핑 100ms까지 보장, 150ms는 보장하지 않는다." 상한을 0.4초로 늘리면 맞힐 수는 있다. 대신 맞는 사람이 0.4초 전 위치에서 맞는다. 그 공정성 비용이 더 크다고 봤다.

사흘 전에도 그랬다. 30발 중 3발만 맞았을 때 범인은 총이 아니라 쓰러진 더미의 몸이었다. 숫자가 이상하면 게임보다 자부터 의심한다. 이번에 그걸 한 번 더 배웠다.

## 보이지 않는 배관

화면에 안 보이는 일도 많았다. 런처로 로그인하면 짧은 게임 표(토큰)를 받고, 게임 서버는 그 표의 서명만 보고 들여보낸다(ADR-330·333). 판이 끝나면 서버가 결과를 먼저 디스크에 쓰고 백엔드로 보낸다(ADR-331). 서버는 백엔드가 배정한 판만 연다(ADR-334). 스쿼드에 혼자 들어가면 봇 팀원을 붙이지 않고 1인 팀으로 뛴다. 이건 내가 정했다(ADR-332).

이슈도 정리했다. 열린 이슈 174개를 코드와 하나하나 대조해 40개를 닫았다. 그런데 내 지시 하나는 틀렸다. 11월 17일 이전 이슈를 한꺼번에 '계획 없음'으로 닫자고 했는데, 다음 날 인수인계서에 "틀렸다"고 적혔다. 오래된 이슈 중엔 이미 구현된 것도 많았다.

## 밤 9시 12분, 대기 섬 첫 삽

오후에 **대기 섬** 기획을 승인했다. 어제 새벽 만든 매칭 대기열의 다음 문제다. 매칭이 잡히고 판이 시작되기까지 최대 90초, 지금은 대기 화면만 본다. 사람이 모이는 게 안 보이니 "이 게임에 사람이 있나" 싶다.

그래서 맵 밖 먼 바다에 지름 80m짜리 밀폐된 섬을 두기로 했다. 걸어 다니고, 번지점프를 하고, 전광판에서 남은 시간을 본다. 섬에서는 아무도 다치지 않는다. 봇도 섬에 모여서 사람처럼 서성인다.

9시 12분부터 21분까지, 9분 동안 티켓 7개가 연달아 커밋됐다. 마지막 T7이 번지점프였고, 높이는 24m(ADR-386)였다.

![대기 섬 커밋 타임라인](img/ep07/diagram_island_timeline.png)
*9분 만에 쓴 섬. 커밋마다 `uncompiled`가 붙었다. 컴파일은 내일이다.*

커밋마다 `uncompiled`가 붙어 있었다. 코드는 썼지만 Unity로 컴파일도 안 해 본 상태라는 뜻이다. 이날 인게임 캡처가 한 장도 없는 것도 그래서다.

밤 11시 7분, 초반 평화 수정이 하나 더 올라갔다. 그런데 봇이 몇 분에 몇 명 죽어야 맞는지, 목표 곡선은 아직 아무도 정하지 않았다. 섬은 컴파일조차 안 됐다.

### 이슈 트리아지 (Issue triage)
할 일 목록(이슈)을 훑어서 "이미 끝남 / 아직 필요함 / 이제 필요 없음"으로 나누는 작업이다. 응급실에서 환자 순서를 정하는 말에서 왔다.

**우리 게임에서는** 열린 이슈 174개를 main 코드·커밋·테스트와 대조해, 근거가 확실한 40개만 닫고 확신이 없는 건 열어 뒀다. 결과는 `docs/ISSUE_RECONCILE_2026-11-18.md`. 반대로 '날짜로 일괄 종료'는 틀린 방법으로 남았다(`docs/MASTER_HANDOFF_3.md` §0).

**왜 중요한가** AI가 하루에 커밋을 수십 개씩 하면 이슈 목록이 금방 현실과 어긋난다. 목록이 틀리면 다음 작업자가 끝난 일을 또 한다.

### 서명 토큰 (HMAC signed token)
"이 사람은 로그인한 누구다"라는 내용 뒤에, 서버만 아는 비밀 키로 만든 서명을 붙인 문자열이다. 원리는 간단하다. 받는 쪽은 같은 비밀 키로 내용의 서명을 다시 계산해서 붙어 온 서명과 비교한다. 내용을 한 글자라도 바꾸면 서명이 안 맞는다. 비밀 키가 없으면 맞는 서명을 만들 수도 없다.

**우리 게임에서는** 백엔드가 5분짜리 토큰을 만들고, 게임 서버가 `Assets/_Project/Scripts/Core/GameToken.cs`에서 백엔드에 묻지 않고 직접 확인한다(ADR-330). 닉네임도 클라이언트가 보낸 값이 아니라 토큰 안의 값을 쓴다. 비밀 키는 저장소에 없고 서버 환경에만 둔다.

**왜 중요한가** 접속할 때마다 백엔드에 묻지 않아도 되니 빠르다. 그리고 남의 이름을 사칭할 수 없다. 대신 비밀 키가 새면 끝이라, 키 관리가 전부다.

### 우선순위 기반 의사결정 (Priority-based decision)
할 수 있는 일 여러 개 중에서, 정해 둔 순서대로 조건을 확인하고 처음 맞는 하나를 고르는 방식이다.

**우리 게임에서는** `Assets/_Project/Scripts/Core/BotPriority.cs`가 탈출 > 교전 > 파밍 > 총성 조사 > 집결 > 이동 순서로 고른다(ADR-312).

```csharp
public static BotGoal Choose(in PriorityInput i)
{
    if (i.EscapeUrgent) return BotGoal.Escape;
    if (i.Combat) return BotGoal.Combat;
    if (i.Farming) return BotGoal.Farm;
    if (i.NoiseHeard && i.Investigates) return BotGoal.Investigate;
    if (i.GatherGoal) return BotGoal.Gather;
    return BotGoal.Travel;
}
```

**왜 중요한가** 순서가 한눈에 보이니 "봇이 왜 저랬지?"를 추적하기 쉽다. 초반 평화도 '교전' 조건을 바꾸는 것만으로 들어갔다.

### 측정 도구 결함 (Harness artifact)
게임은 멀쩡한데, 그걸 재는 테스트 장치(하네스)의 실수 때문에 이상한 숫자가 나오는 것이다.

**우리 게임에서는** `Assets/_Project/Tests/PlayMode/LagCompMatrixTests.cs`. 장전하는 3.5초 동안 표적이 계속 걸어 벽 뒤로 들어갔다. 커밋 `9baf2d4d`에서 장전 중에는 표적을 세우게 고쳤다.

```csharp
// The strafing target must stand still while we reload: 3.5 s of walking carried it to the lane's end, behind the wall
// (every other shot after a reload ended on the wall at x -19.98: a harness artifact, not the compensation).
var moveWas = _net.HostInput.Frame.Move; _net.HostInput.Frame.Move = Vector2.zero;
a.Player.CmdReload(); yield return Frames(3.5f);
_net.HostInput.Frame.Move = moveWas;
```

**왜 중요한가** 0/20을 그대로 믿었다면 멀쩡한 되감기 코드를 뜯어고쳤을 거다. 숫자가 이상하면 고치기 전에 자부터 의심한다.
