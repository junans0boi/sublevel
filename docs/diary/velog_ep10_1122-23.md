# 추측 말고 재 보자 — 게임 제작기 #10 범인은 엘리베이터 문이었다

> 지난 화: 하루에 121커밋, 0.2.0과 0.3.0이 같은 날 나갔다. 11월 21일은 커밋 0개. 그리고 0.3.0을 해 본 말들이 돌아왔다. 물에서 못 나온다. 구급상자가 안 써진다. 그리고 내가 적은 한 줄. "움직이면 1~2초 뒤에 움직여짐."

11/22~23 이틀의 커밋은 35개다. 앞의 날들에 비하면 적다. 대신 이번엔 새 기능이 거의 없다. **고치고 재는 일**만 했다.

## 물에서 못 나오는 이유

11/22 오후 5시, 테스터의 피드백이 이슈가 됐다. "수영하면 물가로 못 올라오고 스페이스 연타도 안 됨."

처음 의심한 건 물가 경사나 턱 높이였다. 원인은 엉뚱한 곳에 있었다. 수영 중엔 자세가 '엎드림'으로 고정되는데, Space로 하는 모서리 잡기는 엎드린 상태를 거절하고 있었다. 5시 11분, 수영 중에도 Space로 물가 턱을 잡고, 낮은 턱은 헤엄쳐 밀기만 해도 올라가게 고쳤다(ADR-552).

## 세 문장

같은 날 나는 세 문장을 던졌다.

> "최적화 위해서 분석합시다."
> "비효율적인 방법을 사용 중인 것들이 있다면 그것도 해결해줘."
> "게임 운영 방식만 다를 뿐 맵과 캐릭터의 상호작용은 동일해야 한다."

마지막 문장은 #8의 그 문 때문이다. 내 컴퓨터가 서버를 겸하는 연습판에선 멀쩡했는데, 실서버에선 문이 안 열렸다. 그때 알았다. 호스트 모드는 실서버를 증명하지 않는다.

5시 59분, 그 차이를 없앴다. 내 컴퓨터가 서버일 때 "어차피 내가 서버니까" 하고 검사를 건너뛰던 지름길이 있었다. 이제 연습판에서도 문 열기 요청이 실서버와 같은 검사를 거친다. 수영과 익사도 전용 서버에서 똑같이 돈다.

7시 11분, 비효율 감사. 봇 코드의 람다 하나가 봇마다 매 프레임 작은 객체를 만들고 있었다. 봇 40명 판에서 프레임당 GC 할당이 5,056 → 2,790바이트로 반이 됐다.

## 추측 말고 재기

8시 44분, 최적화 분석이 올라왔다. 원칙은 하나였다. **추측 말고 재기.** 다른 Unity 작업을 전부 멈춘 독점 창에서 측정만 돌렸다.

결과가 의외였다.

- 그리는 비용은 해상도와 거의 상관이 없었다. 해상도를 0.75배로 줄여도 0.1~0.3ms.
- 진짜 비용은 **멀리 있는 작은 물체를 그리라는 명령의 개수**였다. 1,000번에 약 1.7ms. 보이는 거리를 700m에서 350m로 줄이면 1.4~2.6ms가 빠졌다.

*11/22 20:15 측정용 원경. 비싼 건 해상도가 아니라 멀리 있는 작은 것들*

그래서 작은 물체는 크기별로 150m·300m 밖이면 안 그리게 했다. 대신 **모든 그래픽 프리셋에 같은 거리**를 썼다. 옵션을 낮춘 사람이 먼 엄폐물을 꿰뚫어 보면 안 되니까. 첫 실행 때는 그래픽카드 메모리와 CPU 코어 수를 보고 프리셋을 알아서 고른다(ADR-553). 다음 날 새벽 들어온 "중급 PC에서 진입이 오래 걸리고 렉이 난다"는 피드백도 이 레버로 받았다.

## 1~2초의 범인

그날 밤 나는 분석까지 들어간 빌드(v0.3.0-test1)로 솔로 판을 했다. 그리고 11/23 새벽 1시 53분에 이슈를 남겼다. "움직이면 1~2초 뒤에 움직여짐." 구급상자도 안 써졌다.

처음 의심은 서버였다. 서버가 내 움직임을 이상하다고 보고 되돌리는 게 아닐까. 이번엔 재 봤다. 전용 서버를 코어 2개, 1개로 띄우고, 봇 79명, 지연 100ms에 손실 2%까지 걸었다. 결과는 버튼을 누르고 0.1초 안에 몸이 움직였다. 되돌린 횟수 0. 서버는 범인이 아니었다.

재현된 지연은 딱 한 장면에서 나왔다. 엘리베이터에서 내릴 때다. W를 누른 채로 있으면 문이 가라앉기 시작할 때 입력이 풀린다. 그런데 높이 3.1m 문이 1.2초 동안 내려가면서 충돌체로 길을 막고 있었다. 밖으로 나가는 데 1.21초. 새벽 2시 50분, 문을 0.4초로 줄였다(ADR-555). 섬을 떠난 뒤에도 최대 3초 동안 '아직 섬'으로 판정돼 입력이 막히던 틈도 같이 막았다.

![엘리베이터 문 시간축 수정 전후](img/ep10/diagram_elevator_door.png)
*범인은 엘리베이터 문. 1.2초 동안 길을 막던 문을 0.4초로*

#0부터 나는 엘리베이터에 확신이 없다고 했다. 낙하산이 최선이라고 생각했다. 그 엘리베이터가 이번엔 진짜로 발목을 잡았다. 그것도 문 한 짝이.

구급상자도 비슷했다. 연습판과 멀티의 차이를 의심했는데, 인벤토리 더블클릭이 H키처럼 "지금 제일 알맞은 회복템"을 고르고 있었다. 붕대가 있으면 붕대를 썼다. 이제 누른 그 아이템을 쓴다(ADR-554).

![피드백 세 개의 처음 의심과 실제 원인](img/ep10/diagram_three_bugs.png)

다만 기록엔 단서가 남아 있다. 내가 느낀 게 이 장면이 아니라 **매번 움직일 때마다** 늦는 거라면 실제 빌드, 실제 기기로 다시 봐야 한다. 아직 끝난 문제가 아니다.

## 0.3.1, DX11, 그리고 다시 문

새벽 3시 11분, 고친 것들을 묶어 **0.3.1**.

| 항목 | 전 → 후 |
|---|---|
| 봇 40명 판, 프레임당 GC 할당 | 5,056 → 2,790 바이트 |
| 80인 호스트 메인 스레드 | 8.01 → 6.34 ms |
| 메뉴에서 플레이까지 | 9.9초 → 약 5초 |

아침 9시 25분, Windows 그래픽 API를 자동(DX12)에서 **Direct3D 11 고정**으로 바꿨다(ADR-556). DX12는 셰이더를 처음 쓸 때 그 자리에서 컴파일해서 첫 실행에 멈칫하기 쉽다. 우리는 Mac에서 Windows 빌드를 만들어서 그 비용을 줄일 수단도 적다.

9시 43분엔 `-playtrace`가 생겼다. 봇 연습판을 자동으로 한 판 돌면서 문 열기, 걷기, 줍기, 교전, 차, 수영, 사망, 관전까지 단계마다 프레임과 GC를 남긴다. "키를 누르고 몇 ms 뒤에 움직였나"를 다섯 번 재는 단계도 있다. "늦다"는 내 감을 이제 숫자로 확인할 수 있다.

10시 28분, Windows(Mono) 빌드의 월드 진입이 11.6초에서 4.2초가 됐다. 느렸던 이유가 웃겼다. **문 위치를 알려고** 월드와 건물 설계도를 통째로 다시 만들고 있었다. 그 일만 8.2초. 메뉴 화면에서부터 다른 스레드로 미리 돌리게 했다. 이번 화의 범인은 둘 다 문이었다.

오전 10시 45분, **0.3.2**. 지금 main의 마지막 커밋이다.

## 지금 여기까지

11월 12일 빈 폴더에서 시작해서 커밋 760개. 배그 하기 전에 몸을 풀 연습 게임을 원했다. 똑똑한 봇과 싸우며 운영과 교전을 익히고 싶었다.

![이벤트 경주 주행 화면과 봇 레이서 순위표](img/ep10/event_racing.png)
*11/23 02:31에 찍힌 이벤트 경주. 오른쪽 순위표의 일곱 명은 봇 레이서다*

처음 기획과 가장 달라진 걸 꼽으라면 이거다. **배그를 위한 연습 게임이 아니라, 실제로 배포해 볼 생각이 있는 게임**이 됐다. 런처가 있고, 서버가 있고, 버전 번호가 있다.

그런데 기록을 뒤지다가 알게 된 게 있다. "배그 몸풀기"라는 처음 의도는 어디에도 적혀 있지 않았다. 마음이 "배포할 게임"으로 바뀐 것도 결정 기록이 아니라 이슈 본문(#379)에 한 줄 남았을 뿐이다. 그러니 AI는 그럴듯한 목표를 스스로 세웠다. 배그와의 차이표를 기준 삼아, 판 길이 20~25분에 80명이 들어가는 게임 쪽으로 달려갔다. 나도 같이 달렸다.

의도는 바뀌어도 된다. 다만 **바뀐 걸 적어 두지 않으면, AI는 내가 모르는 방향으로 간다.**

이번 이틀에서 배운 것도 비슷하다. "1~2초 늦다"는 느낌은 맞았지만, 범인에 대한 추측은 틀렸다. 그래서 재야 한다.

그런데 숫자로 못 재는 질문이 하나 남았다. 엘리베이터가 낙하산을 이길까. 처음부터 반신반의했고, 지금도 모르겠다. 그건 직접 해 봐야 안다.

시즌 1은 여기까지다. 0.3.2를 직접 해 보고, 다음 시즌 첫 화를 쓰겠다.

## 📚 이번 회차에 알아두면 좋은 용어

### Direct3D 11과 12, 그리고 PSO 컴파일 (Direct3D 11 vs 12 / PSO Compile Stutter)
**한 줄 정의:** Direct3D는 Windows에서 게임이 그래픽카드에 그림을 시키는 통로(API)다. 12는 더 새롭지만, 셰이더 조합(PSO, 파이프라인 상태 객체)을 **처음 쓸 때** 그 자리에서 컴파일해서 순간 멈칫(스터터)이 생기기 쉽다.

**우리 게임에서는** Windows 빌드만 DX11로 고정했다(ADR-556). `ProjectSettings/ProjectSettings.asset`:

```yaml
  m_BuildTargetGraphicsAPIs:
  - m_BuildTarget: WindowsStandaloneSupport
    m_APIs: 02000000
    m_Automatic: 0
```

`02`가 Direct3D 11, `m_Automatic: 0`은 "자동 선택 안 함"이다.

**왜 중요한가** 평균 프레임이 좋아도 처음 총을 쏠 때 한 번 멈칫하면 플레이어는 "렉 걸린다"고 느낀다. 첫인상을 망치는 멈칫은 평균 숫자에 잘 안 보인다.

### GC, 가비지 컬렉션 (Garbage Collection)
**한 줄 정의:** C#에서 다 쓴 메모리를 알아서 치워 주는 장치. 편하지만 치우는 순간 게임이 잠깐 멈출 수 있다.

**우리 게임에서는** 봇 코드의 람다(이름 없는 함수)가 바깥 변수를 붙잡는 바람에 봇마다 매 프레임 작은 객체가 하나씩 생겼다. 별도 메서드로 빼서 고쳤다. `Assets/_Project/Scripts/AI/BotController.cs`:

```csharp
// (once a frame per bot), though it runs only every 2 s.
static float MetersToBorder(PollutionDirector zones, int own, Vector3 at, Vector3 aim) =>
    BotPollutionPlan.MetersToBorder((x, z) => zones.RegionIndexAt(new Vector3(x, 0f, z)) == own, at.x, at.z, aim.x, aim.z);
```

**왜 중요한가** 이 한 곳이 봇 40명 기준 프레임당 1,280바이트였다(`docs/INEFFICIENCY_AUDIT.md`). 작은 할당도 봇 수만큼 곱해진다.

### 메인 스레드와 워커 스레드 (Main Thread / Worker Thread)
**한 줄 정의:** 화면 갱신은 대부분 메인 스레드 하나에서 돈다. 워커 스레드는 메인과 동시에 도는 일꾼이라, 화면과 상관없는 계산을 맡기면 된다.

**우리 게임에서는** 문 위치 계산(월드·건물 설계도 재생성)을 메뉴 화면 때부터 워커 스레드에서 미리 돌린다. `Assets/_Project/Scripts/Net/DoorSystem.cs`:

```csharp
_layout = Task.Run(() =>
{
    var plan = WorldGenerator.Generate(spec);
    var doors = new List<BuildingOpening>[plan.Lots.Count];
    Parallel.For(0, doors.Length, i =>
    {
        var lot = plan.Lots[i];
        doors[i] = Buildings.Generate(lot.Kind, lot.SizeX, lot.SizeZ, unchecked((int)Hash(plan.Seed, i))).Doors;
    });
    // (이하 생략)
```

**왜 중요한가** Unity 오브젝트를 안 건드리는 순수 계산이라 다른 스레드로 옮길 수 있었다. 덕분에 Mono 빌드 월드 진입이 11.6초에서 4.2초가 됐다.

### 트레이스 로그와 프로파일링 (Trace Log / Profiling)
**한 줄 정의:** 프로파일링은 "어디서 시간이 드는지" 재는 일, 트레이스 로그는 일이 일어난 순서대로 시각과 함께 적는 기록.

**우리 게임에서는** `LoadTrace`가 기준보다 긴 프레임(히치)을 잡으면 스크립트·네트워크 전송·렌더에 각각 몇 ms가 들었는지 적는다. `Assets/_Project/Scripts/Gameplay/LoadTrace.cs`:

```csharp
if (Time.frameCount > 1 && ms > HitchMs && (_stay || Time.realtimeSinceStartup < _watchUntil))
{
    LoadTraceLog.FlushSums();
    Mark($"hitch {ms:F0} ms (scripts {(_lateEnd - (now - ms / 1000.0)) * 1000.0:F0} ms, net send {(_beforeRender - _lateEnd) * 1000.0:F0} ms, render+net read {(now - _beforeRender) * 1000.0:F0} ms)");
}
```

`-playtrace`는 여기에 자동 플레이를 붙여서, 사람이 없어도 같은 순서로 한 판을 돌며 기록을 남긴다.

**왜 중요한가** "느린 것 같다"는 느낌만으로는 고칠 곳을 못 찾는다. 이번에도 범인은 서버가 아니라 문이었다.
