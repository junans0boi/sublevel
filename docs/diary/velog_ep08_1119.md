# 번지 24m는 너무 낮다 — 게임 제작기 #8 대기 섬, 손맛, 그리고 실서버에서 안 열리는 문

> 지난 화: 빈손 봇들이 엘리베이터 문이 열리자마자 주먹싸움을 했고, 나는 "시작 2~3분 만에 30명이 줄어든다"고 했다. 밤 11시 7분 초반 평화 수정이 올라갔지만 목표 곡선은 아무도 정하지 않았다. 9분 만에 쓴 대기 섬은 컴파일조차 안 된 채였다.

## 아침 10시, 곡선에 숫자를 줬다

어제는 "너무 많이 죽는다"까지만 말했다. 그러니 AI는 덜 죽게만 고쳤다. 이번엔 내가 목표를 숫자로 정했다(ADR-317).

- 4분 안에 90% 넘는 봇이 무기를 든다
- 3분 안에 죽는 봇은 8~10명 이하
- 5분 시점에 80명 중 55~65명이 살아 있다

너무 많이 죽어도 안 되고, 너무 안 죽어도 안 된다. 10시 5분, 첫 수정이 올라갔다. 총을 줍기 전엔 싸움을 시작하지 않고, 평화 중엔 먼저 때린 상대에게만 반격한다. 그다음은 재고 고치고 다시 재는 반복이었다.

![시도별 생존 곡선](img/ep08/chart_survival.png)
*180초에 80명이 동시에 총을 꺼내는 장면. 시드 1·2 평균이고, 점은 기록에 남은 측정값만 찍었다(ADR-318~320).*

평화 거리 1m로는 1분 만에 20명이 죽었다. 승강장에 모인 봇끼리 바로 옆에서 쐈다. 거리를 0으로 하고 180초를 주자 3분까지는 아무도 안 죽었다. 그런데 180초가 되는 순간 전원이 동시에 싸워서 1분에 34~35명이 죽었다. 80명이 똑같은 시계를 보고 동시에 총을 꺼내는 장면을 상상하니 좀 웃겼다.

해법은 봇마다 평화가 끝나는 시각을 어긋나게 하는 거였다(ADR-319). 기준을 230초로 미루고(ADR-320), 투입 150초부터 빈손 봇에게 가까운 무기 위치를 알려 줬다(ADR-321). 5분 생존이 59명과 65명, 목표 안에 들어왔다.

봇이 잘 싸우게 만드는 건 어렵지 않았다. 판이 사람처럼 흘러가게 만드는 게 어려웠다.

## 대기 섬: "너무 낮다"

10시 8분, 어젯밤 컴파일도 안 된 채 커밋된 대기 섬이 처음 컴파일을 통과했다. 테스트 1576개도 다 통과였다. 섬에 올라가 번지점프를 해 봤다. 내가 남긴 말은 이렇다.

> 너무 낮다
> 올라가는 길이 보여야 한다
> 고급 고속 엘리베이터처럼

높이를 24m에서 60m로 올리고, 자유낙하는 35m로 늘렸다. 타워 옆에는 밖이 보이는 철골 케이지 승강기를 붙였다. 최고 초속 15m, 60m를 4.8초에 오른다. 출발과 도착은 부드럽게 가속한다(ADR-387). 결국 여기서도 답은 엘리베이터였다.

![케이지 승강기](img/ep08/lift_car_low.png)
*'고급 고속 엘리베이터처럼'의 첫 모습. 녹슨 철골이라 아직 놀이동산은 아니다(11/19 17:52).*

섬을 만든 AI도 "아직 밋밋해서 놀이동산 느낌은 못 냈다"고 스스로 적었다.

## 마스터가 두 번 바뀌었다

이날은 AI 관리자(master)가 두 번 바뀌었다. 11시 20분엔 계정을 옮겨서, 오후 3시 40분엔 토큰이 떨어져서다. 바뀔 때마다 인수인계서를 남겼고, 다음 master가 그걸 읽고 서브 세션을 새로 띄웠다.

내가 한 말은 이거였다. "너가 담당자·관리자, 엄청 중요한 것만 묻고 나머지는 알아서." 그리고 내 맥은 M1이 아니라 M4 Pro라고 몇 번이나 고쳐 줬다. 그제야 Unity를 동시에 3개씩 돌리기 시작했다.

인수인계서에는 반성문 같은 줄도 있다. **"세션이 보고함은 증거가 아니다."** 얼마 전 AI가 옛 캡처를 새것처럼 보내서 내 신뢰를 잃은 일이 있었다. 그 뒤로 master는 캡처의 파일 시각을 확인하고 직접 연 다음에 보고한다.

## 손맛은 전부 내 화면에서만

오후에는 서브 세션 여러 개가 동시에 '손맛'을 채웠다. 먼저 달리기. 나는 전에 "달리기가 ○○ 같다"고 했다(차마 그대로 못 옮기겠다). 재 보니 후진과 옆걸음 때 발이 땅 위에서 초속 2.5~3.5m씩 미끄러지고 있었다.

![수정 전 소총 이동](img/ep08/gait_before_rifle_B.png)
*수정 전 소총 이동 연속 컷. 발 미끄러짐을 재던 장면(11/19 11:50).*

다리 동작을 바꾸고 8방향으로 섞었더니 0.8~1.9m/s로 줄었다(ADR-390·391).

![소총 옆걸음](img/ep08/w3_rifle_sidestep_1.png)
*수정 후 소총 옆걸음. 가슴은 조준 방향을 본다(11/19 15:38).*

그리고 탄피, 재질별 탄흔과 파편, 피, 카메라 흔들림, 쓰러지는 몸(래그돌)이 들어왔다. 볼트 저격총의 탄피는 0.55초 뒤에, 중절식 산탄총은 재장전할 때 한꺼번에 떨어진다.

![탄피가 튀는 장면](img/ep08/w2_casings_flight.png)
*총마다 튀는 시점이 다른 탄피(11/19 15:38).*

![쓰러지는 몸](img/ep08/w1_shot_blood_ragdoll.png)
*맞은 방향으로 쓰러지는 래그돌. 내 화면에서만 그린다(11/19 15:38).*

재밌는 건 이게 **전부 클라이언트 연출**이라는 점이다(ADR-395·396·470·471). 서버 판정과 네트워크 메시지는 하나도 안 바뀌었다. 손맛은 내 화면에서만 만들고, 누가 맞았는지는 서버가 정한다.

오염을 피해 다른 지역으로 가는 열쇠 엘리베이터 규칙도 바꿨다. 팀당 최대 2번, 열쇠 수는 팀 수에 비례. 게임 룰이라 내가 승인했다(ADR-360).

## "통합하고 배포해줘"

오후 3시 20분쯤 브랜치 8개를 한꺼번에 합쳤다. 컴파일 0 에러, 테스트 1632개 통과. 그런데 그다음이 순탄치 않았다.

- PlayMode 테스트 첫 실행에서 Unity가 `Illegal instruction: 4`로 죽었다
- 다시 돌리니 이번엔 디스크가 꽉 찼다
- 세 번째에 진짜 버그가 나왔다. 대기 섬의 '피해 차단'과 봇의 '스폰 보호'가 서로를 부르며 끝없이 돌다 터졌다. 4시 24분, 봇을 섬에 먼저 등록하게 순서를 바꿔 해결했다

메시지 형식이 바뀌었으니 프로토콜 번호도 2에서 3으로 올렸다(ADR-322). 그리고 실서버에 올렸다. 직접 해 봤다.

> 문이 안 열린다
> 차가 적고 안 보인다

원인이 신기했다(ADR-480). 서버(Linux ARM)와 내 맥은 같은 시드로 문 목록을 각자 만든다. 그런데 플랫폼마다 소수점 계산이 아주 조금 달라서 문이 하나 더 생겼다. 그러면 뒤의 문 번호가 전부 한 칸씩 밀린다. 내가 3번 문을 열라고 하면 서버는 엉뚱한 3번 문을 보고 "너무 멀다"며 조용히 무시했다.

![문 번호 밀림](img/ep08/diagram_doors.png)
*같은 시드, 다른 소수점. 번호 대신 위치를 같이 보내서 해결했다.*

5시 35분, 문 메시지에 번호와 함께 문의 위치를 실었다. 차는 20대에서 32대로, 보이는 거리는 350m에서 700m로 늘렸다.

테스트 1632개가 통과해도 문 하나가 안 열렸다. 혼자 하는 호스트 모드에서는 서버와 클라이언트가 같은 컴퓨터라 두 목록이 늘 같다. 그래서 이 버그는 거기서 절대 재현되지 않는다. 결국 실서버에서 문을 열어 본 건 나였다.

밤에 고친 빌드(r5.1)를 다시 해 봤다. 이번엔 "달리는데 느린 조깅 같다." 그리고 배율 조준경이 섬 전체에 열 개쯤밖에 없었다. 자정을 넘겨 1시 1분에 달리기 수정이 올라갔다. 그리고 r5.2에 대한 내 피드백이 쏟아지기 시작한다.

> 다음 화: 피드백 한 줄이 커밋 하나가 되는 날. 그리고 "존버하면 안 끝난다."

## 📚 이번 회차에 알아두면 좋은 용어

### 부동소수점 결정론 (Floating-point determinism)
같은 입력이면 어느 컴퓨터에서든 같은 결과가 나오는 성질을 결정론이라고 한다. 그런데 소수(float) 계산은 CPU 종류나 컴파일 방식에 따라 마지막 자리가 조금 다를 수 있다.

**우리 게임에서는** 서버와 클라이언트가 같은 시드로 문 목록을 각자 만들다 개수가 어긋났다. 그래서 `Assets/_Project/Scripts/Net/DoorSystem.cs`의 `Resolve`가 번호가 맞지 않으면 위치로 문을 다시 찾는다(ADR-480).

```csharp
public int Resolve(int index, Vector3 at)
{
    if (index >= 0 && index < _doors.Count && (At(index) - at).sqrMagnitude < 0.25f) return index;
    EnsureGrid();
    _grid.Query(at.x, at.z, 1f, _near);
```

**왜 중요한가** "같은 시드면 같은 맵"은 같은 플랫폼에서만 안전하다. 서버와 클라이언트의 플랫폼이 다르면 위치처럼 어긋나도 버티는 기준이 필요하다.

### 오브젝트 풀링 (Object pooling)
자주 생겼다 사라지는 물체를 매번 새로 만들지 않고, 미리 만들어 둔 것을 돌려 쓰는 기법이다. 만들고 지우는 비용과 메모리 청소(GC) 때문에 생기는 끊김을 줄인다.

**우리 게임에서는** `Assets/_Project/Scripts/Gameplay/CasingFx.cs`의 `CasingPool`이 탄피를 최대 40개(효과 낮음 12개)만 두고 가장 오래된 것부터 다시 쓴다.

```csharp
int cap = Capacity;
if (_next >= cap) _next = 0;
int i = _next;
_next = (_next + 1) % cap;
ref var c = ref _cases[i];
if (c.T == null && !Make(ref c)) return;
```

**왜 중요한가** 80명이 동시에 총을 쏘면 탄피가 끝없이 생긴다. 상한과 재사용이 없으면 물체가 쌓여 프레임이 무너진다.

### 블렌드 트리 (Blend tree)
걷기, 달리기, 옆걸음 같은 애니메이션 여러 개를 캐릭터의 속도와 방향에 맞춰 섞어 주는 Unity 기능이다. 2D 블렌드 트리는 앞뒤 속도와 좌우 속도 두 값으로 섞는 비율을 정한다.

**우리 게임에서는** `Assets/_Project/Editor/CharacterControllerBuilder.cs`가 코드로 8방향 2D 블렌드 트리를 만든다(ADR-391).

```csharp
var state = controller.CreateBlendTreeInController(name, out var t, 0);
t.blendType = BlendTreeType.FreeformDirectional2D;
t.blendParameter = CombatantAnimation.MoveX;
t.blendParameterY = CombatantAnimation.MoveZ;
foreach (var c in children) t.AddChild(Clip(c.clip), c.at);
```

**왜 중요한가** 동작마다 그 동작의 실제 발 속도 자리에 놓아야 발이 안 미끄러진다. 미끄러짐을 2.5~3.5m/s에서 0.8~1.9m/s로 줄인 것도 이 배치를 고친 결과다.

### 클라이언트 전용 연출 (Client-side cosmetics)
게임 결과에는 영향이 없고 보는 사람 화면에서만 그리는 효과다. 서버는 "쐈다", "맞았다"만 알리고, 탄피나 피나 쓰러지는 몸은 각 컴퓨터가 그 소식을 보고 알아서 그린다.

**우리 게임에서는** `Assets/_Project/Scripts/Gameplay/CasingFx.cs`는 이미 오가던 사격 이벤트(`ShotFired`)에 붙기만 한다. 래그돌(`CombatantRagdoll.cs`)은 총알·시야 판정에 안 걸리는 레이어에 있고, 줍기 같은 서버 판정은 쓰러진 몸이 아니라 사망 위치 기준이다(ADR-395).

```csharp
void Awake()
{
    _combatant = GetComponent<Combatant>();
    _weapons = GetComponent<WeaponVisual>();
    _combatant.ShotFired += OnShot;
}
```

**왜 중요한가** 손맛을 더할 때마다 네트워크 메시지를 늘리면 80명 판의 대역폭이 버티지 못하고, 서버와 화면이 어긋날 곳도 는다. 연출을 판정에서 떼어 놓으면 프로토콜 버전을 안 올리고도 손맛을 계속 더할 수 있다.
